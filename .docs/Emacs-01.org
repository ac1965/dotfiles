** 1. はじめに
:PROPERTIES:
:CUSTOM_ID: 導入
:END:
ソフトウェア開発を進めるうえで、どのツールを選び、どう使いこなすかは、日々の作業効率に大きく影響します。数あるエディタの中でも、GNU Emacs は「高い拡張性」と「豊富なパッケージ資産」を武器に、統合開発環境として今なお根強い支持を得ています。

本文書では、Emacs を代表するパッケージである *Org mode*（文書・タスク管理機能）と *Magit*（Git操作インターフェース）を取り上げ、これらを組み合わせることで生産性とメンテナンス性をどのように高められるかを、具体例を交えながら丁寧に解説します。初めてこれらのツールに触れる方でも理解できるよう、専門用語にはできるだけ補足を添えています。

*** 1.1 Emacsとは何か
:PROPERTIES:
:CUSTOM_ID: emacsの概要
:END:
GNU Emacs は 1976年に開発が始まった、非常に長い歴史を持つテキストエディタです。最大の特徴は、独自のプログラミング言語である Emacs Lisp を使って、動作をほぼ自由にカスタマイズできる点にあります。単なる「文字を編集するソフト」にとどまらず、文書作成・タスク管理・プログラムのバージョン管理まで、開発に関わる作業をひとつの画面に集約できるハブのような存在です。

- 拡張性の高さから「OSのようなエディタ」と呼ばれることもあります。設定次第でメール閲覧やファイル管理まで行えるためです。
- Emacs Lisp を使えば、利用者自身が新しい機能を作ったり、既存の動作を変更したりできます。
- 世界中の開発者が今も活発にコミュニティ開発を続けており、新しいパッケージが日々公開されています。

*** 1.2 Org modeとは
:PROPERTIES:
:CUSTOM_ID: org-modeとは
:END:
Org mode は、Emacs 上で動く多機能な情報管理システムです。ひとつのテキストファイルの中で、タスク管理・文書作成・日記・プログラムの実行までをまとめて扱えるのが大きな魅力です。主な特長は以下のとおりです。

- 見出しを階層的に作成し、必要な部分だけを開いたり折りたたんだりできる（長い文書でも迷いにくい）
- `TODO`、`DONE` などのキーワードを見出しに付けて、タスクの進み具合を記録できる
- `SCHEDULED`（着手予定日）や `DEADLINE`（締切日）を指定して、スケジュールを管理できる
- `#+BEGIN_SRC` というブロックの中にプログラムコードを書き、そのまま実行して結果を表示できる
- `C-c C-e`（このコロン区切りの表記は「Ctrlキーを押しながらc、続けてe」という操作を意味します）を使えば、LaTeX・HTML・Markdown など様々な形式に文書を書き出せる

このように、見た目は普通のテキストファイルでありながら、「プロジェクト管理」「文書執筆」「プログラミング」を1つのファイルの中で自然につなげられるのが Org mode の強みです。

*** 1.3 Magitとは
:PROPERTIES:
:CUSTOM_ID: magitとは
:END:
Magit は、Emacs の中だけで完結する Git 操作用のインターフェースです。Git はコマンドライン（CLI）で操作するのが一般的ですが、コマンドを正確に覚える必要があり、慣れるまでにやや時間がかかります。Magit を使うと、変更内容を画面で見ながら視覚的に操作できるため、学習のハードルがぐっと下がります。

- 変更差分を「ハンク」と呼ばれる細かい単位で選び、ステージング（コミット対象に含めること）／アンステージング（対象から外すこと）ができる
- コミットする前に、どこがどう変わったのか、これまでの履歴とあわせて画面上ではっきり確認できる
- ブランチの作成やリベース（履歴の付け替え）といった操作も、メニューから選ぶだけで完結する
- 複数のリモートリポジトリ（GitHubなど外部の保管場所）をまとめて管理できる

コマンドを1文字ずつ手入力する CLI に比べ、Magit は「今何が起きているか」が見やすいぶん、操作ミスを防ぎやすいという利点があります。

** 2. Org modeで生産性を高める
:PROPERTIES:
:CUSTOM_ID: orgモードによる生産性向上
:END:
Org mode は、個人の小さなタスク管理から、規模の大きい文書作成まで幅広く対応できる、Emacs の中核機能のひとつです。ここでは代表的な使い方と設定例、そして実際に運用する際に押さえておきたいポイントを順を追って紹介します。

*** 2.1 タスク管理とTODO機能
:PROPERTIES:
:CUSTOM_ID: タスク管理とtodo機能
:END:
Org mode では、見出し行の先頭に `TODO` や `DONE` といった状態（ステータス）を書き添えることで、タスクを階層構造のまま管理できます。プロジェクトの大きな流れと、個々の細かい作業の両方を同じファイルで見渡せるのが便利な点です。

**** 2.1.1 TODOキーワードを自分好みに設定する
状態の種類（キーワード）は、あらかじめ決められたものだけでなく、自分のプロジェクトに合わせて自由に定義できます。

#+begin_src emacs-lisp
(setq org-todo-keywords
      '((sequence "TODO(t)" "IN-PROGRESS(i)" "REVIEW(r)" "|" "DONE(d)" "CANCELLED(c)")))
#+end_src

上の設定例では、「未着手（TODO）→ 作業中（IN-PROGRESS）→ レビュー中（REVIEW）→ 完了（DONE）または中止（CANCELLED）」という流れを定義しています。括弧内のアルファベット（`t`、`i` など）は、その状態にワンタッチで切り替えるためのショートカットキーです。こうしてプロジェクトの実態に合ったタスクの一生（ライフサイクル）を設計できます。

**** 2.1.2 実践例：プロジェクトのタスクリスト
実際にタスクを書くと、次のような見た目になります。

#+begin_src org
,* TODO 新機能の設計
  SCHEDULED: <2024-10-01 Tue>
  :PROPERTIES:
  :EFFORT: 4:00
  :END:
,** IN-PROGRESS フロントエンド構成検討
,** REVIEW データモデル設計
,** DONE 競合調査
   CLOSED: [2024-09-20 Fri 15:00]
#+end_src

`EFFORT` は見込み作業時間、`SCHEDULED` は着手予定日、`CLOSED` は完了した日時を表します。このように、タスクに付随する情報をまとめて1か所に記録できるため、あとから振り返るときにも役立ちます。

**** 2.1.3 タスク管理の基本操作手順
実際に手を動かす際の操作の流れをまとめると、次のようになります。

1. `C-c C-t` を押して、タスクの状態（TODO / IN-PROGRESS など）を切り替える
2. `C-c .` を押して、`SCHEDULED` や `DEADLINE` の日付を入力する
3. 作業を始めるときは `C-c C-x C-i` を押し、時間の記録を開始する
4. 作業が終わったら `C-c C-x C-o` を押し、時間の記録を終了する
5. タスクが完了したら、あらためて `C-c C-t` を押して `DONE` に変更する

この一連の流れを習慣にすると、「今何をしていて、あとどれくらいかかったか」が自然と記録として残ります。

*** 2.2 文書作成とアウトライン機能
:PROPERTIES:
:CUSTOM_ID: 文書作成とアウトライン機能
:END:
Org mode は、見出しを階層的に並べる「アウトライン構造」をベースに文書を組み立てます。`TAB` キーで見出しの開閉ができるため、文書全体が長くなっても、今どこを見ているのか迷いにくいのが特長です。

**** 2.2.1 文書構造の設計例
たとえばシステムの仕様書であれば、次のように章立てを組めます。

#+begin_src org
,* システム概要
,** 背景と目的
,** 要件定義
,** 実装方針
,*** バックエンド構成
,*** API設計
,*** デプロイ戦略
#+end_src

見出しの階層（`*` の数）が深くなるほど、より細かいテーマを扱っていることを表します。全体を俯瞰したいときは上位の見出しだけを開いておき、詳細を確認したいときだけ該当箇所を展開する、という使い方ができます。

**** 2.2.2 いろいろな形式に書き出す（エクスポート）
`C-c C-e` を使うと、Org ファイルを次のような形式に変換して出力できます。

- HTML：そのままWeb上で公開できる文書に変換
- LaTeX → PDF：印刷や配布に適した、見た目の整った文書を作成
- Markdown：GitHub の README など、他のツールとも相性がよい形式
- ODT：Microsoft Word などと互換性のある形式

LaTeXへの変換をよく使う場合は、あらかじめ以下のように出力コマンドを指定しておくとスムーズです。

#+begin_src emacs-lisp
(require 'ox-latex)
(setq org-latex-pdf-process '("latexmk -pdf -f %f"))
#+end_src

*** 2.3 アジェンダ機能でスケジュールを管理する
:PROPERTIES:
:CUSTOM_ID: アジェンダとスケジュール管理
:END:
Org mode の大きな魅力のひとつが、タスクに日付情報を持たせることで、日々の予定づくりまで Emacs 内だけで完結できる点です。この仕組みを「アジェンダ」と呼びます。

**** 2.3.1 アジェンダ画面の使い方
よく使う代表的なコマンドは次のとおりです。

- `C-c a a`：1週間分の予定を一覧表示する
- `C-c a t`：すべての TODO タスクを一覧表示する
- `C-c a s`：条件を指定して、より詳しく検索する

表示の仕方は、以下のように設定でカスタマイズできます。

#+begin_src emacs-lisp
(setq org-agenda-start-on-weekday 1) ; 月曜始まりにする
(setq org-agenda-span 7)             ; 表示範囲を1週間分にする
#+end_src

**** 2.3.2 作業時間を記録して、生産性を見える化する
Org mode では、タスクにどれだけ時間をかけたかを記録する「クロック機能」も備わっています。

#+begin_src emacs-lisp
(setq org-clock-persist 'history)
(org-clock-persistence-insinuate)
#+end_src

上の設定を入れておくと、Emacsを再起動しても記録の履歴が保持されます。実際の記録は、次のように残ります。

#+begin_src org
,* TODO 実装フェーズ
  :LOGBOOK:
  CLOCK: [2024-09-19 Thu 10:00]--[2024-09-19 Thu 12:00] =>  2:00
  CLOCK: [2024-09-18 Wed 13:00]--[2024-09-18 Wed 15:30] =>  2:30
  :END:
#+end_src

この記録をもとに、「どの作業にどれだけ時間を使っているか」を後から振り返ることができ、見積もりの精度向上にも役立ちます。

**** 2.3.3 アジェンダ設定でつまずきやすいポイント
運用する中でよくある注意点を、あらかじめ知っておくと安心です。

- `org-agenda-files` に登録するファイルの数が多すぎると、アジェンダ表示の起動が遅くなることがあります。必要なファイルだけに絞りましょう。
- 週の始まりの曜日（`org-agenda-start-on-weekday`）を変更した場合は、カレンダー表示との対応関係にずれが出ていないか確認してください。
- 予定のはずのタスクがアジェンダに表示されないときは、`SCHEDULED` や `DEADLINE` の日付が正しく設定されているか、まず疑ってみましょう。

*** 2.4 コードブロックで「文書とコード」を一体化する
:PROPERTIES:
:CUSTOM_ID: コードブロックとリテラルプログラミング
:END:
Org mode は、説明文とプログラムコードを同じファイルの中に共存させる「リテラルプログラミング」という考え方をサポートしています。コードの説明と、そのコード自体、さらに実行結果までを1つの文書にまとめられるため、後から読み返したときの理解のしやすさが大きく向上します。

**** 2.4.1 Pythonコードを埋め込んで実行する
たとえば、次のように書くと、Org ファイルの中で直接 Python コードを実行できます。

#+begin_src org
,#+BEGIN_SRC python :results output
print("こんにちは、Orgからの出力です！")
,#+END_SRC
#+end_src

コードを実行すると、その結果は自動的に `#+RESULTS:` という行の下に挿入されます。手作業で結果をコピー＆ペーストする必要がないため、コードと結果が常に一致した状態を保てます。

**** 2.4.2 複数のプログラミング言語を組み合わせて使う
Org mode は50を超える言語の実行に対応しており、1つの文書の中で複数の言語を使い分けることもできます。

- Python、R、Shell、JavaScript
- SQL、Emacs Lisp、C++
- Rust、Go、Clojure など

これらの言語を使うには、あらかじめ次のように「どの言語を有効にするか」を設定しておく必要があります。

#+begin_src emacs-lisp
(org-babel-do-load-languages
 'org-babel-load-languages
 '((python . t)
   (shell . t)
   (emacs-lisp . t)
   (sql . t)))
#+end_src

**** 2.4.3 コードブロックを使うときの注意点
実際に使ってみると、いくつかつまずきやすいポイントがあります。

- 各言語を実行するには、先ほどの `org-babel-load-languages` にその言語をあらかじめ登録しておく必要があります。登録し忘れると実行時にエラーになります。
- Pythonのコードブロックを実行するには、パソコン自体に Python がインストールされている必要があります。
- `:results output` と指定すると、標準出力（print文などの内容）が `#+RESULTS:` に反映されます。もし結果が表示されない場合は、誤って `:results value`（戻り値だけを表示する設定）になっていないか確認してください。

**** 2.4.4 リテラルプログラミングの運用手順
日常的にコードブロックを活用する際の流れは、次のようになります。

1. `#+BEGIN_SRC` と `#+END_SRC` の間にコードを書く
2. カーソルをブロック内に置き、`C-c C-c` を押して実行する
3. 実行結果が自動的に `#+RESULTS:` の下に挿入される
4. 同じブロックを再実行すると、古い結果は新しい結果に上書きされる
5. コードを変更したら都度実行し直すことで、文書とコードの内容を常に一致させておく

この習慣を続けることで、「書いてあるコードは本当に動くのか」を後から疑う必要がなくなり、文書の信頼性が保たれます。

*** 2.6 Org文法の基礎（実例で確認する）
:PROPERTIES:
:CUSTOM_ID: org文法の基礎構文
:END:
最後に、ここまで登場した記法を1つのサンプルにまとめておきます。実際に手元で試しながら確認してみてください。

#+begin_src org
,* 見出し（レベル1）
,** 見出し（レベル2）

,* TODO タスクのタイトル
  DEADLINE: <2025-09-30 Tue>
  SCHEDULED: <2025-09-21 Sun>

,#+BEGIN_SRC python :results output
print("Hello from Org!")
,#+END_SRC

,#+RESULTS:
: Hello from Org!
#+end_src

💡 `#+` から始まる行は「ディレクティブ」と呼ばれ、エクスポートの設定やコード実行の指示など、文書そのものではなく「Orgに対する指示」を書くために使われます。文中に見慣れない `#+` の行が出てきたら、この点を思い出してください。

** 3. Magitでバージョン管理を効率化する
:PROPERTIES:
:CUSTOM_ID: magitによるバージョン管理の効率化
:END:
Magit は Emacs 内で完結する Git のフロントエンド（操作画面）であり、コマンドライン操作に比べて、視覚的にも操作性の面でも優れた Git 体験を提供してくれます。ここでは、Git 初心者の方にも、すでに CLI に慣れている上級者の方にも役立つ活用方法と設定のポイントを解説します。

*** 3.1 Git操作をシンプルにする
:PROPERTIES:
:CUSTOM_ID: git操作の簡素化
:END:

**** 3.1.1 Magitの基本操作の流れ
まずは基本の操作手順を覚えましょう。

1. `C-x g` を押して、Magit のステータス画面を開く
2. `s` キーで、変更内容をステージング（コミット対象に追加）する
3. `c c` で、コミットを作成する画面へ進む
4. `P p` でリモートへプッシュする、または `F p` でリモートからプルする
5. `q` を押して、Magit のバッファ（画面）を閉じる

**** 3.1.2 差分を見ながら、必要な部分だけをステージする
- 差分（変更内容）は `TAB` キーで展開・折りたたみができ、どこがどう変わったかを細かく確認できます。
- ステージ操作（`s`）を、ファイル単位ではなく個別の「ハンク」（変更のかたまり）単位で実行すると、その部分だけをコミット対象に含められます。

これにより、1つのファイルに複数の変更が混ざっていても、意味のあるまとまりごとに分けてコミットできるようになります。たとえば「バグ修正」と「見た目の調整」を同じファイルで行った場合でも、それぞれ別々のコミットとして記録できるのです。

*** 3.2 ブランチを管理する
:PROPERTIES:
:CUSTOM_ID: ブランチ管理
:END:

**** 3.2.1 主なブランチ操作コマンド

| 操作             | キーバインド | 説明                                   |
|------------------+--------------+----------------------------------------|
| ブランチ作成     | b c          | 新しいブランチを作成してチェックアウトする |
| ブランチ切替     | b b          | 既存のブランチに切り替える             |
| ブランチ削除     | b k          | 不要になったブランチを削除する         |
| ブランチリスト   | y            | すべてのブランチを一覧表示する         |

**** 3.2.2 ブランチ運用で気をつけたいこと
- `main` や `develop` といった主要なブランチには、直接コミットしないようにしましょう。作業は必ず別のブランチで行い、レビューを経てから取り込むのが安全です。
- チームで開発する場合は、`feature/*`（新機能用）、`bugfix/*`（不具合修正用）のような命名規則を決めておくと、ブランチの目的が一目でわかり管理しやすくなります。
- ブランチを統合する際は、履歴を1本にまとめたいのか（rebase）、統合の記録も残したいのか（merge）によって、適切な方法を選びましょう。

*** 3.3 コミットとマージを使いこなす
:PROPERTIES:
:CUSTOM_ID: コミットとマージ
:END:

**** 3.3.1 コミット作成の基本の流れ
1. `C-x g` で Magit を起動する
2. `s` で変更をステージングする
3. `c c` でコミット作成画面に移動する
4. コミットメッセージを編集し、`C-c C-c` で確定する

💡 **ちょっとした小技**：`c e` を使うと、変更内容を含まない「空コミット」も作成できます。バージョンにタグを打ちたいだけのときなどに便利です。

**** 3.3.2 コミットメッセージの書き方のルール
読みやすいコミットメッセージには、次のような型があります。

- 1行目：変更の要点を、50文字以内を目安に簡潔にまとめる
- 2行目：空行を1行入れる
- 3行目以降：必要であれば、変更の背景や詳細を書き加える

例を挙げます。

#+begin_example
feat: APIエンドポイントの認証を追加

- JWTトークンの検証を追加
- 401レスポンスのテストケースを追加
#+end_example

このように書いておくと、後から履歴を見返したときに「何を」「なぜ」変更したのかがすぐにわかります。

**** 3.3.3 マージ戦略の選び方と注意点

| 戦略               | 用途                               | 注意点                             |
|--------------------+------------------------------------+------------------------------------|
| Fast-forward       | シンプルな一直線の履歴で統合する   | 統合の記録自体が残らないことがある |
| Three-way merge    | マージした事実を履歴として明示的に残す | コンフリクト（競合）発生時は手動での対応が必要 |
| Rebase             | 履歴を1本の線のようにきれいに保つ  | 共有中のブランチで使うと履歴が混乱するおそれがある |
| Squash             | 複数の変更を1つのコミットにまとめる | 個々の変更の履歴は残らなくなる     |

どの戦略が正解というわけではなく、プロジェクトの方針やチームの合意に応じて選ぶことが大切です。

*** 3.4 リモートリポジトリを操作する
:PROPERTIES:
:CUSTOM_ID: リモートリポジトリ操作
:END:

**** 3.4.1 リモートの追加と基本操作の流れ
1. `C-x g` で Magit を起動する
2. `M` の後に `a` を押し、新しいリモート（例：`origin`、`upstream`）を追加する
3. `F` の後に `p` でプル、`P` の後に `p` でプッシュする

**** 3.4.2 リモート運用で押さえておきたいこと
- `origin`（自分の作業元リポジトリ）だけでなく `upstream`（フォーク元のリポジトリ）も設定しておくと、元のプロジェクトとの同期がしやすくなります。
- 本番環境へのデプロイ用など、目的の異なるリモートは名前を分けて登録しておくと、誤って意図しない場所にプッシュしてしまう事故を防げます。
- リモートのURLを変更したいときは、`magit-remote-set-url` というコマンドで簡単に更新できます。

** 4. Org modeとMagitを組み合わせて使う
:PROPERTIES:
:CUSTOM_ID: 統合的な活用方法
:END:
Org mode と Magit を組み合わせると、文書・タスク・コード・履歴という、開発に関わる要素のすべてをひとつの環境の中で管理できるようになります。ここでは、実際の開発の流れに沿った、実践的な統合ワークフローを手順とともに紹介します。

*** 4.1 プロジェクト全体を管理する
:PROPERTIES:
:CUSTOM_ID: プロジェクト管理
:END:

**** 4.1.1 プロジェクト構成の例
たとえば、次のようなディレクトリ構成を考えてみます。

#+begin_src org
project-root/
├── README.org              # プロジェクト概要（Org形式）
├── docs/
│   ├── specification.org   # 仕様書
│   ├── meeting-notes.org   # 会議録
│   └── development.org     # 開発ログ
├── src/                    # ソースコード
├── tests/                  # テストコード
└── .git/                   # Gitリポジトリ
#+end_src

ドキュメント類もソースコードと同じリポジトリの中で管理することで、コードと文書のバージョンを常に対応させておくことができます。

**** 4.1.2 典型的な統合ワークフローの手順
1. `specification.org` に、Org mode で要件を書き出す
2. その内容を `development.org` の中で、実際のタスクへと分解する
3. 各タスクに `TODO` ラベルと日付を設定し、スケジュールを組み立てる
4. 実装作業中は `org-clock-in` で時間を記録しながら、`src/` 内のコードを編集する
5. `C-x g` で Magit を開き、変更をステージしてからコミットする
6. タスクが完了したら `C-c C-t` を押して `DONE` に更新する

このように、企画から実装、記録までの一連の流れを、Emacsという1つの環境の中で完結できます。

*** 4.2 ドキュメントを管理する
:PROPERTIES:
:CUSTOM_ID: ドキュメント管理
:END:

**** 4.2.1 ドキュメントのライフサイクル例

| 段階     | 使用ファイル            | 操作内容                                     |
|----------+-------------------------+----------------------------------------------|
| ドラフト | specification.org       | Org modeで仕様を書き出す。タスク化も可能     |
| レビュー | featureブランチ         | Gitでレビューを行い、Magitで差分を確認する   |
| 公開     | HTML/PDF/Markdown化     | `C-c C-e` で目的の形式にエクスポートする     |
| 保守     | development.org         | 更新履歴を記録し、Gitで差分を管理し続ける    |

**** 4.2.2 バージョン管理のベストプラクティス
- コードだけでなく、文書もこまめに `commit` することで、変更の履歴を残しておきましょう。
- 文書の変更だけをまとめる `docs` ブランチを、コード用のブランチとは分けて用意するのも有効な方法です。
- Org の `:LOGBOOK:` を使えば、文書自体の更新履歴も見える化できます。

*** 4.3 日々のワークフローを最適化する
:PROPERTIES:
:CUSTOM_ID: ワークフロー最適化
:END:

**** 4.3.1 日次の開発ルーチン例
1. `C-c a a` でその日のアジェンダを確認する
2. `C-c C-x C-i` で作業時間の記録を開始する
3. `src/` 内で実際の作業を進め、進捗を `development.org` に書き留める
4. `C-x g` で Magit を開き、変更をコミットする
5. `C-c C-x C-o` で作業時間の記録を終了する
6. `C-c C-t` を押して、完了したタスクを `DONE` に変更する

**** 4.3.2 状況に応じたテンプレートの活用
- `org-capture` を使うと、バグ報告や会議の議事録などを、思いついたその場ですぐに記録できます。
- プロジェクトごとに `capture templates`（記録用のひな形）を分けておくと、情報が散らからず整理された状態を保てます。
- `org-id` という機能を使うと、文書同士をリンクでつなげられるため、関連する情報を一元的にたどれるようになります。

** 5. 実践的な設定例とTips
:PROPERTIES:
:CUSTOM_ID: 実践的な設定例とtips
:END:
このセクションでは、Org mode と Magit を実際に導入・運用していくうえでおすすめしたい設定や、日々の開発効率を高めるための実践的なコツを紹介します。

*** 5.1 初期設定を最適化する
:PROPERTIES:
:CUSTOM_ID: 初期設定の最適化
:END:

**** 5.1.1 Org modeの設定例と注意点

#+begin_src emacs-lisp
(require 'org)
(setq org-directory "~/org")           ;; Orgファイルの基本置き場所
(setq org-agenda-files '("~/org"))     ;; アジェンダの対象にするファイル群
#+end_src

- `org-directory` は、日記・タスク・メモなどを1か所に集約するための起点になる場所です。この場所自体をGitで管理するのもおすすめです。
- `org-agenda-files` に指定するファイルは、必要最小限にとどめましょう。数が多すぎると、アジェンダの表示に時間がかかる原因になります。

#+begin_src emacs-lisp
(setq org-todo-keywords
      '((sequence "TODO(t)" "IN-PROGRESS(i)" "WAITING(w)"
                  "|" "DONE(d)" "CANCELLED(c)")))
#+end_src

- タスクの状態遷移を、実際のプロジェクトの進め方に合わせて定義しておくことで、ワークフロー自体が明確になります。

**** 5.1.2 Magitの設定例と注意点

#+begin_src emacs-lisp
(require 'magit)
(setq magit-refresh-status-buffer nil)   ;; パフォーマンス改善のための設定
(setq git-commit-summary-max-length 50)  ;; コミットメッセージ1行目の推奨文字数
(setq magit-diff-refine-hunk 'all)       ;; 差分内の変更箇所を強調表示する
#+end_src

- `magit-refresh-status-buffer` を無効にしておくと、規模の大きいリポジトリでも画面の読み込みが遅くなりにくくなります。
- `magit-diff-refine-hunk` を有効にすると、行の中のどこがどう変わったかまで色分けされ、差分の見やすさが向上します。

**** 5.2.1 キーバインドをカスタマイズする例
:PROPERTIES:

- Magit については、特に `C-x g` の操作に慣れておくと、日常的な作業がぐっとスムーズになります。

**** 5.2.2 org-captureのテンプレートを活用する例
:PROPERTIES:
:CUSTOM_ID: org-captureテンプレートの活用例
:END:

#+begin_src emacs-lisp
(setq org-capture-templates
      '(("t" "Task" entry (file+headline "~/org/tasks.org" "Tasks")
         "* TODO %?
  SCHEDULED: %t
")
        ("m" "Meeting" entry (file+headline "~/org/meetings.org" "Meetings")
         "* %? :meeting:
  %U

** Attendees
** Agenda
** Notes
")
        ("j" "Journal" entry (file+datetree "~/org/journal.org")
         "* %?
  %U
")))
#+end_src

- `file+headline` を指定すると、記録した内容が指定した見出しの下に自動的に追加されます。
- `%U`、`%t`、`%?` は「テンプレート展開コード」と呼ばれるもので、それぞれ記録した日時、着手予定日、カーソルを置く位置を自動的に埋め込んでくれます。

:PROPERTIES:
:CUSTOM_ID: チーム開発での活用

**** 5.4.1 .dir-locals.elで設定をチームに共有する
:PROPERTIES:
:CUSTOM_ID: dir-locals-elによる共通設定

#+begin_src emacs-lisp
((org-mode . ((org-todo-keywords .
               (sequence "TODO" "IN-REVIEW" "TESTING"
