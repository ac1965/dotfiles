* 概要

本書は GNU Emacs 本体（C コア + Lisp 層）の内部構造を、ソフトウェア設計書の
体裁でまとめたものである。目的は次の 2 点。

- Emacs の「なぜこう動くか」を、主要コンポーネント単位で把握できるようにする
- 拡張（elisp パッケージ）を書く／内部を改造する際に、影響範囲を見積もれるようにする

対象は =emacs-mirror/emacs= の master ブランチ（2026-09 時点、バージョン
=32.0.50=、直近リリースは emacs-31.1）を実ソースで確認した内容を基準とし、
Emacs 29〜32 で入った主要変更（tree-sitter の本格導入、Android/Haiku 移植、
native-comp のデフォルト化など）を反映する。

** 設計思想（3行まとめ）

- *"Lisp machine" 思想* :: エディタの大部分を Lisp（Emacs Lisp）で書き、
  性能が必要な最小限の部分だけを C で実装する。C 層は「小さな Lisp 処理系 +
  低レベルプリミティブ集」に徹する。
- *拡張性優先* :: ほぼ全ての振る舞い（キー割り当て、表示、コマンド）が
  実行時に Lisp から再定義できる。固定仕様がほぼ存在しない。
- *単一プロセス・シングルスレッド中心* :: 表示・編集・Lisp 実行は基本的に
  1 つのメインループ上で協調的に進む（非同期処理はプロセス/スレッド/タイマー
  で補助的に実現）。Lisp スレッド（=make-thread=）はあるが、同時に実行できる
  Lisp コードは常に 1 つだけという GIL 的な制約を持つ。

- 起動時、C の =main()=（=emacs.c=）が最小限の初期化を行った後、
  =lisp/loadup.el= を読み込み、Lisp レベルの初期化（多数の =.el= ファイルの
  ロード）を行ってから =temacs= を dump（*pdumper* 形式）して実行可能な
  =emacs= バイナリを生成する。旧来の =unexec= 方式は多くのプラットフォームで
  廃止済みで、pdumper が標準の起動高速化機構になっている。
- 通常起動時はこの dump イメージを読み込むため、Lisp 標準ライブラリの
  再パースを省略でき、起動が高速になる。
- GUI バックエンドは X11/Cocoa/Windows(GDI)/Pure GTK に加え、Emacs 30 以降は
  *Android*（=androidterm.c= / =androidfns.c=）、*Haiku OS*
  （=haikuterm.c= / =haikufns.c=）にも正式移植されており、1 つのソースツリーが
  多数のプラットフォームバックエンドを =#ifdef= で切り替える構成になっている。

* Lisp インタプリタ・評価器

** データ型と =Lisp_Object= 表現

すべての Lisp 値は C 側では =Lisp_Object= という単一のワード幅整数型で
表現される。下位数ビットをタグとして使い、型を判別する（tagged pointer
方式）。代表的なタグは次の通り。

- =Lisp_Int0= / =Lisp_Int1= :: fixnum（immediate、ヒープ確保不要）
- =Lisp_Symbol= :: シンボル（オフセットベースのポインタ表現）
- =Lisp_String= :: 文字列（ヒープ上の =struct Lisp_String=）
- =Lisp_Vectorlike= :: ベクタ、ハッシュテーブル、バッファ、ウィンドウ、
  フレーム、プロセス、記録型（record）、native-comp 関数、tree-sitter
  パーサ/ノードなどの可変長構造体を包含する総称タグ
- =Lisp_Cons= :: コンスセル
- =Lisp_Float= :: 浮動小数点数

=Lisp_Vectorlike= が「なんでも入れられる箱」になっている点が特徴的で、
バッファ・ウィンドウ・フレームといった「オブジェクトっぽいもの」は実体としては
すべてこのベクタ風構造体の一種として実装されている。

** eval ループ

- Lisp コードはまず =lread.c= の =read1()= により S 式（Lisp オブジェクトの
  木構造）へパースされる。
- =eval.c= の =Feval= がこの木を評価する。関数呼び出しはシンボルの
  function cell を辿って以下のいずれかに分岐する。
  1. スペシャルフォーム（=if=, =let=, =setq= など。C 関数として直接実装）
  2. マクロ（展開してから再評価）
  3. 通常関数（Lisp 関数 or C 組み込み =subr=）
  4. バイトコンパイル済み関数（=bytecode.c= の VM へ）
  5. native-comp 済み関数（後述）
- 関数呼び出しのたびに C の再帰呼び出しスタックが伸びるため、深い再帰は
  =max-lisp-eval-depth= で制限される。

** シンボルと束縛（動的束縛 / レキシカル束縛）

- 各シンボルは *value cell*・*function cell*・*plist*（属性リスト）を持つ。
- 伝統的に Emacs Lisp は *動的スコープ（dynamic binding）* を採用しており、
  =let= はグローバルな value cell を一時的に退避・復元する形で実現される
  （=specbind= / =unbind_to=）。
- Emacs 24 以降、ファイル先頭に =;;; -*- lexical-binding: t -*-= を書くことで
  *レキシカルスコープ* を選択できる。この場合、束縛はクロージャオブジェクト
  内の環境リストとして保持され、コンパイラ最適化の余地が広がる。
- Emacs 30 以降、バイトコンパイラは =lexical-binding= cookie が無いファイルに
  対して警告を出すようになり、新規に書く Lisp コードは事実上レキシカル束縛が
  標準（推奨）という位置づけになった。ただし後方互換のため動的束縛モードは
  引き続きサポートされ、ファイル単位で混在しうる。

** ガベージコレクション

- master ブランチ（Emacs 32 系）でも引き続き *保守的マーク&スイープ方式*
  （=alloc.c=）が標準の GC である。GC 対象は cons セル・文字列・ベクタ・
  シンボル・浮動小数点数など種類ごとに固定サイズブロックで確保される
  （=struct cons_block= のような block allocator）。
- =garbage-collect= はスタック・レジスタ・グローバルルート（=staticpro= された
  変数群）から到達可能なオブジェクトをマークし、未到達のブロックを回収する。
- GC 中は基本的に Lisp 実行が停止する（stop-the-world）。GC 閾値
  （=gc-cons-threshold= / =gc-cons-percentage=）の調整で発生頻度を制御できる。
- Ravenbrook 社の MPS（Memory Pool System）を使った *igc*（incremental
  garbage collector）は別フィーチャーブランチで開発が続けられているが、
  本書執筆時点（2026-09、master =32.0.50=）ではまだ master にはマージされて
  おらず、標準ビルドには含まれていない。将来のメジャーバージョンで取り込まれる
  可能性がある点は留意しておく。

** バイトコンパイラ / バイトコード VM

- =lisp/emacs-lisp/bytecomp.el= が S 式をスタックマシン向けバイトコード
  （文字列にエンコードされた命令列 + 定数ベクタ）へ変換する。
- 実行は =bytecode.c= の =exec_byte_code= が単純なディスパッチループで
  行う。関数呼び出しオーバーヘッドが減るぶん、素の =eval= より高速。
- ほとんどの標準ライブラリ（=lisp/*.elc=）はあらかじめバイトコンパイル済みで
  配布される。

** native-comp（ネイティブコンパイル）

- Emacs 28 で libgccjit を用いた Emacs Lisp → 機械語（=.eln= ファイル）の
  事前 / 遅延コンパイル機能が統合された（=comp.el= / =comp.c=）。
- Emacs 30 以降、=configure= はビルド環境に libgccjit があればデフォルトで
  native-comp を有効化するようになり、「オプション機能」から「標準機能」へと
  位置づけが変わった。無効化するには明示的に =--without-native-compilation=
  を指定する必要がある。
- バイトコードより大幅に高速化できる一方、C コンパイラチェーン
  （libgccjit）への依存が増える。
- 呼び出し規約やスタックの扱いが通常の Lisp 関数とは異なるため、GC やデバッガ
  との連携には専用の橋渡しコードが存在する。=.eln= ファイルは
  =native-comp-eln-load-path= 配下のキャッシュディレクトリに保存され、
  =describe-function= 等でどの関数がネイティブコンパイル済みかを確認できる。

** tree-sitter 連携（構文木パーサ）

- Emacs 29 で =treesit.c= を通じた tree-sitter（インクリメンタル構文解析
  ライブラリ）バインディングが導入され、Emacs 30/31 で対応メジャーモード
  （=*-ts-mode=）が急速に拡充された（Elixir, HEEx, Lua, PHP, TypeScript 等）。
- tree-sitter パーサ／ノードは =Lisp_Vectorlike= の一種として Lisp オブジェクト
  化され、Lisp 側から構文木への問い合わせ（クエリ、ノード走査）ができる。
- Emacs 30 以降、tree-sitter モードは対応する非 tree-sitter メジャーモードの
  サブモードとして宣言され、=major-mode-remap-alist= により自動的に
  tree-sitter 版へリマップされる。ハイライト・インデント・
  =show-paren-mode=/=hs-minor-mode= との統合ルールも tree-sitter 版の
  「thing」定義（=treesit-thing-settings=）を介して提供される。
- 各言語のパーサは =libtree-sitter-<lang>.so/.dylib/.dll= として実行時に
  動的ロードされ、=treesit-language-source-alist= からのビルド/インストールを
  =treesit-install-language-grammar= が支援する。

* バッファ・テキスト管理

** バッファの内部構造（gap buffer）

- 各バッファのテキストは *gap buffer*（ギャップ付き連続配列）として保持される。
  編集点付近に「隙間（gap）」を持たせ、その位置での挿入・削除を O(1) に近い
  コストで行う。カーソル位置が大きく移動するとギャップの再配置
  （=move_gap= 相当の処理）が発生する。
- マルチバイト対応のため、実際には「バイト単位のオフセット」と
  「文字単位のオフセット」を両方管理する（=charpos= と =bytepos= の二重管理）。
- バッファはさらに narrowing（=narrow-to-region=）により「見かけ上の
  先頭・末尾」を制限できる。

** マーカー（Marker）

- マーカーはバッファ中の「位置」を指すオブジェクトで、その位置より前で
  テキストが挿入・削除されると自動的に位置がずれる（追従する）。
- 実装上は各バッファが自身に属するマーカーの連結リストを保持し、
  =insdel.c= のテキスト変更処理の中でそれらの位置を一括更新する。
- ポイント（カーソル位置, point）自体も概念的にはマーカーに近いが、
  実際は各バッファ構造体が直接 =pt= / =pt_byte= フィールドとして保持する
  （バッファを表示するウィンドウごとに独立した point を持てる）。

** テキストプロパティ / オーバーレイ

- *テキストプロパティ* :: 文字列やバッファの各文字位置に紐づく属性
  （フォント、色、キーマップ、クリック時の動作など）。区間木的な
  interval tree（=INTERVAL= 構造体）で管理され、挿入・削除時に自動的に
  引き継がれる／分割される。
- *オーバーレイ* :: バッファ上の「区間」に紐づく属性オブジェクトで、
  テキストプロパティと異なりテキスト本体には格納されず、バッファに
  外付けされる。前後の境界の扱い（開区間・閉区間）を柔軟に指定できる
  （例: 構文ハイライトの一時マーキング、diff 表示の追加行マークなど）。
- どちらも表示エンジン（=xdisp.c=）が redisplay 時に参照し、face
  （文字装飾）の合成やクリック領域の判定に使われる。tree-sitter ベースの
  フォントロックもテキストプロパティ（=font-lock-face=）経由で表示に反映される。

** バッファローカル変数

- Emacs Lisp の変数はデフォルトではグローバルだが、
  =make-local-variable= 等でバッファ単位の値を持てる。
- 実装上、シンボルの value cell とは別にバッファ構造体側に
  ローカル値を保持するスロット（連想的な仕組み）があり、変数アクセス時に
  「現在のバッファにローカル値があるか」をまず確認する。
- メジャーモードの大半の設定（インデント幅、コメント記法など）はこの
  仕組みの上に成り立っている。

* 表示エンジン・ウィンドウ管理

** フレーム / ウィンドウ / バッファの階層

#+begin_example
Frame (OS 上の 1 ウィンドウに相当。X11/Cocoa/GTK/Windows/Android/Haiku/端末)
 └── Window Tree（二分木: 水平/垂直分割ノード + 葉ウィンドウ）
       └── 葉ウィンドウ each shows exactly one Buffer at a time
#+end_example

- *フレーム* は GUI/端末上の実ウィンドウに対応する最上位コンテナ。
  対応バックエンドは =xterm.c=（X11）、=w32term.c=（Windows）、
  =nsterm.m=（macOS Cocoa）、=pgtkterm.c=（Pure GTK, Wayland を含む）、
  =androidterm.c=（Android）、=haikuterm.c=（Haiku OS）、=term.c=
  （文字端末）と多岐にわたる。
- *ウィンドウ* は分割によりできる矩形領域で、内部的には二分木構造
  （=struct window= が親・子・兄弟ポインタを持つ）として管理される。
  葉ノードのみが実際にバッファを表示する。
- 同じバッファを複数ウィンドウに表示できるが、各ウィンドウは独立した
  point・スクロール位置・narrowing 状態を持てる。

** redisplay（再描画）の仕組み

- =xdisp.c= が Emacs 最大のソースファイルで、redisplay 全体を統括する。
  主要な流れ:
  1. どのバッファ／ウィンドウが「再描画が必要か」を検知
     （バッファ変更、ウィンドウサイズ変更、point 移動などの各種フラグ）。
  2. 各ウィンドウについて、表示すべき行を先頭から glyph（描画単位。文字・
     アイコン・継続行マーカーなど）の並びに変換する（*glyph matrix* の構築）。
  3. 直前のフレームの glyph matrix と新しい glyph matrix を比較し、
     差分のみを実際の画面／端末に描画する（=dispnew.c=）。
- この差分更新の仕組みにより、大きなバッファでも変更のあった行付近だけを
  再描画すればよく、パフォーマンスが保たれる。
- redisplay は「Lisp を実行しながら割り込まれる」ことがあるため、
  Emacs 特有の *redisplay 中の再入* 問題（フック内で編集操作をしてよいか等）
  に神経を使う設計になっている。

** フォント・文字集合・多言語対応

- 文字コードは内部的に Emacs 独自の拡張文字集合（かつての MULE、現在は
  Unicode を中心にした統一的な内部表現）で扱われる。
- =font.c= がプラットフォームごとのフォントバックエンド（Xft, Cairo,
  Core Text, GDI, HarfBuzz など）を抽象化し、face（文字装飾の集合: フォント・
  色・太字/斜体など、=xfaces.c=）と組み合わせて実際のグリフを解決する。
- =sfnt.c=（約 21,000 行）は Emacs 自前の TrueType/OpenType フォント
  ラスタライザで、外部フォントライブラリに依存できない／したくない環境
  （Android 移植など）で使われる組み込みフォントバックエンドである。近年の
  ソースツリーで最も急成長したファイルの一つ。
- 合字・結合文字・双方向テキスト（BiDi）は =composite.c= や
  bidi 関連ロジックが担当する。

** 埋め込みウィジェット（xwidget）

- =xwidget.c= は WebKitGTK（GTK 系）や macOS の WKWebView 等をバッファ内に
  埋め込む =xwidget-webkit= 機能を提供する。通常の glyph ベースの描画とは
  別に、ネイティブなサブウィジェットをウィンドウ領域に重ねて描画する仕組みで、
  ドキュメントプレビューや簡易ブラウザ用途に使われる。

* 入力処理とコマンドループ

** キーマップとキーバインディング

- キーマップは「キー列 → コマンド（または別のキーマップ）」を対応付ける
  連想構造（実体は特殊なリスト/ベクタ、=keymap.c= が解釈）。
- *アクティブなキーマップの重ね合わせ順* が重要な設計要素:
  1. オーバーレイ・テキストプロパティが指定するキーマップ
  2. マイナーモードのキーマップ（有効な順）
  3. メジャーモードのキーマップ
  4. グローバルキーマップ
  この優先順位により、同じキーでも文脈依存の挙動を実現している。

** コマンドループ（command loop）

- =keyboard.c= の =command_loop_1= がメインループで、次を繰り返す:
  1. 入力イベントを 1 つ読む（キー入力、マウス、タイマー、プロセス出力など
     すべて「イベント」として統一的に扱われる）。
  2. アクティブなキーマップ群からイベント列に対応するコマンドを検索する
     （プレフィックスキーの場合は次のイベント待ちに遷移）。
  3. 解決したコマンド（Lisp 関数）を =call-interactively= 経由で実行する。
  4. 実行後、redisplay をトリガーする条件を満たしていれば再描画。
- タイマー・非同期プロセス出力・シグナルなども「イベント」としてこのループに
  合流するため、Emacs は事実上シングルスレッドのイベント駆動アーキテクチャで
  ある（Lisp スレッド機能はあるが、同時に走る Lisp コードは常に 1 つという
  GIL 的な単一実行制約を持つ）。

** フック / アドバイス機構

- *フック* :: 特定タイミングで呼ばれる関数リストを保持する変数
  （例: =before-save-hook=）。パッケージはここに関数を追加することで
  コア機能を変更せずに振る舞いを拡張できる。
- *アドバイス（advice）* :: 既存関数そのものを動的に包み替える機構
  （=advice-add= / =nadvice.el=）。関数呼び出し前後に処理を差し込んだり、
  戻り値・引数を書き換えたりできる、より強力で危険度の高い拡張手段。

* 拡張機構

** パッケージシステム（package.el / ELPA・MELPA）

- =package.el= がリモートリポジトリ（GNU ELPA, NonGNU ELPA, MELPA 等）
  からのパッケージ取得・インストール・依存解決・ロードパス登録を担う。
- パッケージは基本的に 1 つ以上の =.el=（または tar 形式のディレクトリ）
  として配布され、ヘッダコメントに依存パッケージやバージョンをメタ情報として
  記述する規約になっている。

** メジャーモード / マイナーモード

- *メジャーモード* :: バッファに 1 つだけ有効化できるモード。ファイル種別
  ごとの構文・インデント・キーマップ・フェイス定義をまとめる単位
  （例: =prog-mode= 系列, =text-mode= 系列）。多くは =define-derived-mode=
  で既存モードを継承して定義する。近年は同じ言語に対して非 tree-sitter 版と
  =*-ts-mode= 版が並存し、=major-mode-remap-alist= でどちらを使うか制御する
  構成が増えている（[[* tree-sitter 連携（構文木パーサ）][3.7 節]]参照）。
- *マイナーモード* :: 複数同時に有効化できる、横断的な機能単位
  （例: =flyspell-mode=, =company-mode=）。=define-minor-mode= で
  トグル変数・キーマップ・モードライン表示をまとめて定義できる。

** プロセス・IPC（サブプロセス／ネットワーク）

- =process.c= がサブプロセス起動（pipe/pty）、ネットワークソケット、
  シリアルポートなどを統一的な「プロセスオブジェクト」として扱う。
- プロセスの入出力は非同期に行われ、出力が届くとコマンドループのイベントとして
  Lisp 側のフィルタ関数・センチネル関数が呼ばれる。これにより
  LSP クライアント（eglot 等）や shell 連携、compilation-mode などが
  ノンブロッキングに実現されている。

** 動的モジュール（dynamic module）

- =emacs-module.c= / =emacs-module.in.h= が、C/Rust 等で書かれた共有
  ライブラリ（=.so=/=.dylib=/=.dll=）を =module-load= で動的ロードし、
  Lisp から呼び出せる関数として登録する ABI を提供する（Emacs 25 以降）。
- ABI はバージョニングされており（=module-env-25.h= 〜 =module-env-32.h=）、
  新しいランタイム機能を追加しつつ古いモジュールとの互換性も保つ設計に
  なっている。tree-sitter とは独立した仕組みだが、いずれも「重い処理を
  C/ネイティブ側に逃がす」拡張手段という点で位置づけが近い。

** 組み込みデータ処理ライブラリ（JSON / SQLite）

- =json.c= が jansson ライブラリを利用した高速な JSON パース／シリアライズ
  （=json-parse-string= 等）を C レベルで提供する（Emacs 27 以降）。LSP
  （Language Server Protocol）通信など、大量の JSON を捌く用途で使われる。
- =sqlite.c= が SQLite データベースへの組み込みバインディングを提供し
  （Emacs 29 以降）、パッケージが外部プロセスを起動せずに構造化データを
  永続化できる。

* ファイル I/O・永続化

- ファイルの読み書きは =fileio.c= が担当し、文字コード変換
  （=coding.c= のコーディングシステム）や改行コード変換を挟んでバッファへ
  展開・書き出しを行う。
- オートセーブ（=auto-save-mode=）、バックアップファイル作成、
  ロックファイル（同時編集検知）など、データ保全のための周辺機構も
  このレイヤーに含まれる。
- 起動時の永続化として、初期状態の高速ロードのために *pdumper*
  （portable dumper）がヒープ全体をイメージとしてシリアライズ／
  デシリアライズする仕組みを提供している。旧来の =unexec= 方式は多くの
  プラットフォームで廃止され、pdumper が事実上の標準になっている。

* 付録: 静的解析による裏付け

本章は上記の記述を裏付ける／補強するために、対象ソースツリー
（=src/=, =lib-src/=, =lwlib/=）に対して実際に静的解析ツールを走らせた結果の
要約である。詳細な生ログ・再実行手順は同リポジトリの =analysis/= 配下
（=analysis/README.md=）を参照。解析対象は macOS（Cocoa/NS バックエンド）
向けにコンパイルされた 88 ファイル（=compile_commands.json= ベース、

** clang-tidy: =Lisp_Object= タグ付きポインタ設計の裏付け

- =bugprone-signed-bitwise=（約 21,300 件）、=performance-no-int-to-ptr=
  （約 6,400 件）といった警告が突出して多く検出された。これは
  [[* データ型と =Lisp_Object= 表現][3.1 節]]で述べた「=Lisp_Object= は
  単一ワードに型タグをビット埋め込みする」設計が、C レベルでは符号付き整数への
  ビット演算・整数⇔ポインタ変換の多用として実際に現れていることの定量的な
  裏付けになっている。バグではなく、意図された低レベル表現である。
- =bugprone-reserved-identifier=（約 14,100 件）は主に gnulib 由来ヘッダの
  =_GL_XXX= 系マクロによるもので、Emacs 固有の設計とは無関係のノイズ。
- =bugprone-macro-parentheses=（約 4,200 件）は =DEFUN= マクロ等、
  伝統的な C プリプロセッサマクロを多用する実装スタイル（[[* 主要ソースファイルと責務（抜粋、行数はおおよその目安）][2.2 節]]）を反映している。
- 経路依存解析（=clang-analyzer-*=）は相対的に少数（NullDereference 28件、
  ArrayBound 18件、DeadStores 256件など）で、こちらの方が実バグ調査の
  優先候補になりうる。ただし xdisp.c/font.c/keyboard.c 等で検出された
  NullDereference の多くは、呼び出し側の不変条件を解析器が追い切れていない
  典型的な誤検知パターンに見え、断定には個別レビューが必要である。

** cppcheck: 検出はごく少数

- =--force=（全 =#ifdef= 組み合わせ網羅）は組み合わせ爆発で非現実的な時間が
  かかったため =--max-configs=1= で実行。検出はわずか 6 件で、うち実質的に
  意味があるのは =lib-src/ebrowse.c= の =nullPointer=（3040行目）と
  =identicalConditionAfterEarlyExit=（524行目）の 2 件のみ。
  =ebrowse.c= は C タグ生成ツール（=lib-src/= 配下の周辺ツール群の一つ）で
  あり、Emacs コア（=src/=）自体からは有意な cppcheck 検出は無かった。

** tree-sitter: =DEFUN= マクロが構文解析を阻害する

- 公式 =tree-sitter-c= グラマーでそのままパースすると、成功率は
  =src/= で 11.8%（18/152）、=lib-src/= で 41.7%、=lwlib/= で 50.0% と低い。
- 原因は Emacs の関数定義の大半が独自マクロ =DEFUN(...)= を使い、その引数に
  =doc: /* ... */= という非標準トークン列を含むため、プリプロセッサ展開なしの
  生文法では =ERROR= ノードになってしまうこと。[[* tree-sitter 連携（構文木パーサ）][3.7 節]]で説明した
  tree-sitter 統合は *Emacs Lisp* 側の構文解析（=treesit.c= 経由）の話であり、
  Emacs 自身の *C 実装コード* を tree-sitter で解析する場合はこの制約に
  別途対処が必要になる、という区別に注意。
- 逆に =DEFUN= を使わないユーティリティ層（=alloc.c=, =font.c=, =frame.c=,
  =treesit.c=, =composite.c=, =sfnt.c= など）はクリーンにパースできており、
  ソースツリー内でも「Lisp から呼ばれる境界層」と「純粋な内部ユーティリティ」
  で C コードのスタイルに差があることが伺える。

** ctags / cscope

- Universal Ctags で約 31,000 タグ、cscope データベースを生成済み。
  関数定義・呼び出し元の横断検索に利用できる（=analysis/tags=,
  =analysis/cscope.out=、いずれも生成物のため本リポジトリの Git 管理対象外）。

** lisp/ 標準ライブラリの解析: 「薄い C 層」説の検証

C コアだけでなく =lisp/=（1,677 ファイル、約 203 万行。C コアの約4倍の規模）
も同じ観点で解析し、[[* 設計思想（3行まとめ）][1.1 節]]で述べた
「"Lisp machine" 思想」を定量的に裏付けた。

- *バイトコンパイル警告*: 全 1,653 ファイルを強制再コンパイルして
  警告 57 件・エラー 0 件（詳細は =analysis/reports/byte-compile-warnings.txt=）。
  この規模（約 46,000 関数）に対する少なさは、標準ライブラリが CI で
  継続的にバイトコンパイルチェックされていることの裏付け。内容のほとんどは
  「非推奨関数/変数を非推奨の文脈から参照している」パターンで、実バグと
  言えるものは「レキシカル引数がダイナミック変数をシャドウする」警告
  3 件程度に留まった。
- *tree-sitter*: 汎用の =tree-sitter-elisp= グラマーでの構文解析成功率は
  *98.8%（1,657/1,677）*。C コアの成功率（11.8%、[[* tree-sitter: =DEFUN= マクロが構文解析を阻害する][11.3 節]]）とは対照的に
  ほぼクリーンにパースできる。C 層は =DEFUN= マクロ等の独自プリプロセッサ
  記法に阻まれる一方、Lisp 層は素直な S 式であるため一般的なツールでも
  容易に解析できる——という差そのものが「C 層は薄いプリミティブ集合、
  実際のロジックの大半は素直な Lisp で書かれる」という設計思想の
  もう一つの裏付けになっている。失敗した 20 ファイルはいずれも
  Unicode 文字属性の自動生成データテーブル（=international/uni-*.el=）等、
  巨大なリテラルが原因でコード構造の問題ではない。
- *ctags*: 84,964 タグ（関数 46,170・変数 14,445・カスタム変数 9,366 等）。
  =(require ...)= 依存が多い＝結合度が高いファイルは =org/org.el=（25）や
  =gnus/message.el=（17）など、org-mode・Gnus が突出して大きな依存グラフを
  持つサブシステムであることが分かった。これは [[* メジャーモード / マイナーモード][7.2 節]]で述べた
  「メジャーモードが機能単位として大規模化しうる」実例と言える。

** 他バックエンド（pgtk）でのビルド確認

[[* フレーム / ウィンドウ / バッファの階層][5.1 節]]で挙げた複数バックエンドのうち、本書の解析は主に macOS/NS
ビルドでコンパイルされる範囲に限られていた。追加で Homebrew 経由の GTK3・
X11 クライアントライブラリを導入し、=--with-pgtk --without-ns= で
out-of-tree（VPATH）ビルドを実施したところ、pgtk バックエンドは正常に
ビルド・pdump まで成功した。NS ビルドには存在しない pgtk 固有 12 ファイル
（=pgtkterm.c=, =pgtkfns.c=, =gtkutil.c=, =xsettings.c= 等）を特定して
clang-tidy を実行したところ、カテゴリ内訳は NS ビルドと同様の傾向
（=bugprone-signed-bitwise= 等が上位）であり、[[* clang-tidy: =Lisp_Object= タグ付きポインタ設計の裏付け][11.1 節]]で述べた
=Lisp_Object= タグ付きポインタ設計の裏付けはバックエンドを問わず一貫して
いることを確認した（要約: =analysis/reports/clang-tidy-pgtk-summary.txt=）。
なお Windows（w32）・Android・Haiku バックエンドはクロスコンパイル環境が
必要なため今回は未検証。

** 構造・依存関係抽出: =#include= グラフ / DEFUN レジストリ / 呼び出しグラフ

ここまでの解析（11.1〜11.6）は主に「リンタ警告のカテゴリ集計」だったが、
本節では一段掘り下げて、tree-sitter の AST 統計値だけでは分からない
*構造そのもの*（どのヘッダが中心的か、どの関数がどこから呼ばれるか）を
grep / ctags / cscope ベースで抽出し、[[* レイヤー構成][2.1 節]]・[[* eval ループ][3.2 節]]・[[* ガベージコレクション][3.4 節]]・
[[* コマンドループ（command loop）][6.2 節]]の記述を実データで裏付ける。tree-sitter の役割は「規模・複雑度の
定量情報（AST ノード数・パース成否）」に限定し、構造抽出・依存関係抽出は
=DEFUN= マクロ等に阻まれない grep/ctags/cscope が担う、という分業で実施した
（generic な tree-sitter クエリで =DEFUN= 展開後の構造を追おうとすると
11.3 節と同じ理由で信頼性が落ちるため）。

=emacs.c=（43）, =xterm.c=（30）, =keyboard.c=（27）, =xdisp.c=（27）。
=emacs.c= が =main()= を持つエントリポイントとして最多の fan-out を持つのは
自然だが、=xterm.c=/=keyboard.c=/=xdisp.c= が僅差で続く点は、
[[* 主要ソースファイルと責務（抜粋、行数はおおよその目安）][2.2 節]]の行数ランキングとも整合し、「行数が多いファイルほど多くの
サブシステムと直接連携する」傾向を裏付ける（詳細:
=analysis/reports/c-include-graph.json=）。

*** DEFUN レジストリ（Lisp 可視プリミティブの実数）

=src/*.c= 中の =DEFUN(...)= 宣言を機械的に数えたところ、Lisp から直接
呼び出し可能な組み込み関数（=subr=）は *1,848 個*、105 ファイルに分布して
いた（=analysis/reports/defun-registry.txt=）。上位は
=window.c=（121）, =data.c=（120）, =fns.c=（104）, =editfns.c=（80）,
=frame.c=（69）— いずれも [[* バッファ・テキスト管理][4 節]]・[[* 表示エンジン・ウィンドウ管理][5 節]]で説明した「Lisp から
直接操作されるオブジェクト」を扱うファイル群と一致する。

対照的に =xdisp.c= は DEFUN 24 個/ctags 検出関数 407 個（比率 5.9%）と
極端に低く、[[* redisplay（再描画）の仕組み][5.2 節]]で述べた「redisplay はほぼ内部完結した処理で、Lisp からは
薄いインタフェースしか露出しない」設計を定量的に裏付けている。

なお =data.c=（DEFUN 120 / ctags 関数 60 = 比率 200%）のように 100% を
超えるファイルが複数あり、これは **ctags の汎用 C パーサも =DEFUN= マクロを
一部取りこぼす**（11.3 節で述べた tree-sitter ほど深刻ではないにせよ同種の
限界がある）ことを示している。定量比較には注意が必要で、DEFUN 数の方が
信頼できる一次情報である。

*** cscope による呼び出しグラフのスポットチェック

アーキテクチャ上重要な関数について実際の呼び出し元を cscope で確認した
（=analysis/reports/call-graph-spotcheck.txt=）:

- =garbage_collect= の直接呼び出し元は =maybe_garbage_collect=（しきい値
  チェック付きラッパー、=alloc.c=）と =android_on_low_memory=（OS からの
  低メモリ通知）の *2 箇所のみ*。[[* ガベージコレクション][3.4 節]]で述べた「GC はしきい値に基づき
  トリガーされる」という記述が、実装上も単一の関門関数
  （=maybe_garbage_collect=）に集約されていることを確認した。
- =maybe_gc=（GC 発生チェック）の呼び出し元は =exec_byte_code=
  （バイトコード VM）、=eval_sub=（eval ループ）、=read_char=
  （キー入力読み取り）の 3 箇所。[[* eval ループ][3.2 節]]で述べた評価ループと、
  [[* コマンドループ（command loop）][6.2 節]]で述べた入力読み取りの両方が GC チェックポイントになっており、
  「Lisp コードが一歩でも進めば GC 機会がある」設計であることが分かる。
- =command_loop_1=（[[* コマンドループ（command loop）][6.2 節]]で述べたメインループ本体）は cscope の直接呼び出し
  検索では *呼び出し元 0 件* だった。実際には =keyboard.c:1163= の
  =internal_condition_case (command_loop_1, handlers, cmd_error)= で
  *関数ポインタとして* 渡されており、直接呼び出しではなくコールバック
  登録の形を取っている。これは「コマンドループ全体を条件処理
  （condition-case 相当）でラップし、トップレベルのエラーを一括捕捉する」
  という C レベルの実装パターンを示しており、静的な呼び出しグラフ抽出
  だけでは見えない「関数ポインタ経由の制御フロー」が Emacs のエラー処理
  ([[* フック / アドバイス機構][6.3 節]]の外側にあるトップレベルの安全網)に使われている実例である。

*** lisp/ の require/provide 依存グラフ

`analysis/reports/elisp-require-graph.txt` より、最も多くのファイルから
=(require ...)= されているフィーチャは *=cl-lib=（438 ファイル）*で、
2 位の =org-macs=（125）を大きく引き離す。=cl-lib=（Common Lisp 由来の
マクロ・関数集合）が事実上「第二の標準ライブラリ」として lisp/ 全体の
1/4 以上のファイルに浸透している実態は、本書がこれまで触れていなかった
観点であり、Emacs Lisp を書く／読む上での実務的な前提として付記する価値が
ある。require 数（fan-out）が多い＝結合度が高いファイルは
=org/org.el=（42）, =calc/calc-ext.el=（40）で、[[* lisp/ 標準ライブラリの解析: 「薄い C 層」説の検証][11.5 節]]の ctags 分析結果
（=require= 数トップの =org.el=）と一致する。
